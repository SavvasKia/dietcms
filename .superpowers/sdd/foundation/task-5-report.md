## Follow-up Risks

1. **`tenant_members` has no RLS.** The RLS policy on `notes` uses a subquery on `tenant_members`. Since `authenticated_backend` can read ALL rows in `tenant_members` (no policy restricts it), a compromised session can enumerate which users belong to which tenant via a direct query on that table. This is intentional for the spike, but real domain tables must add RLS on `tenant_members` before any user-facing feature exposes membership data.

2. **`tenants` has no RLS.** Same concern — `authenticated_backend` can read all tenant metadata.

3. **Single-tenant assumption in policy.** The policy uses `limit 1` on the `tenant_members` subquery. If a user ever belongs to multiple tenants (e.g., an admin user), only one is matched. Multi-tenancy for a single user will require a revised policy (e.g., using `= ANY(subquery)`).

4. **Pool lifecycle.** The `authedPool` in `db/authed-client.ts` is a module-level singleton. In serverless edge deployments, pool teardown must be handled carefully — this is fine for Neon serverless (WebSocket pool) but worth noting.
